# ADR-0007. Конструктор сайта: страницы из блоков в БД, каталог услуг и цен

- Статус: **принято** (2026-10-16, решение Свята)
- Зависит от: ADR-0002 (мастер-данные), ADR-0003 (Blazor), ADR-0005 (веб-админка), ADR-0009 (сейчас SQL Server, перед продом PostgreSQL)

## Контекст
Клиника должна сама менять сайт: порядок и состав разделов, тексты, фото, врачей, услуги, без программиста и без пересборки.
Цены на сайте обязаны совпадать с реальными. По ADR-0002 мастер услуг и цен — МИС (до её выбора цены живут в ClinicHub).
Сейчас контент лежит в файле `site-content.json`, а набор и порядок разделов зашиты в код.

## Варианты
| Вариант | + | − |
|---|---|---|
| **Блоки из набора** (страница = упорядоченный список типизированных блоков) | дизайн и мобильная вёрстка не ломаются; SEO и доступность гарантирует код; объём работ разумный | новый тип блока добавляет программист |
| Свободная вёрстка (как Tilda) | полная свобода | в разы дольше; легко сломать вид на телефоне; сложно с доступностью и SEO |
| Внешняя headless CMS (Strapi, Directus) | готовый редактор | второй стек (Node), ещё один сервер в клинике, данные в чужой модели |

## Решение

### 1. Страницы из блоков
- `Page` — адрес (`/`, `/uslugi`, `/akcii/…`), заголовок, SEO-поля, признак публикации.
- `PageVersion` — версия страницы: `Draft` / `Published` / `Archived`. Редактируется только черновик; «Опубликовать» превращает черновик в новую опубликованную версию. Старые версии остаются, поэтому можно откатиться.
- `Block` — блок внутри версии: тип, порядок, видимость, данные — JSON в текстовой колонке (переносимо, ADR-0009). Для каждого типа в коде есть класс настроек (C# record), компонент отрисовки и форма редактора.
- Набор блоков на старте: обложка (hero), быстрая запись, услуги (карточки), прайс-лист, врачи, до/после, отзывы, каналы, статьи, текст, акция, FAQ, контакты, призыв к записи.
- Текстовые блоки принимают ограниченную разметку (абзацы, жирный, списки, ссылки) и проходят санитайзер. Произвольный HTML/JS в блоки вставить нельзя (защита от XSS и от поломки вёрстки).

### 2. Каталог услуг, врачей и цен — отдельно от страниц
- `ServiceCategory`, `Service`, `Doctor`, `DoctorService`. У услуги есть название, описание для сайта, цена «от», длительность, видимость на сайте и порядок.
- **Блоки цены не хранят.** Блок «Услуги» или «Прайс» хранит только выбор (категория или список id), а цена при отрисовке берётся из каталога. Поэтому цена правится в одном месте и меняется на всём сайте сразу.
- У записей каталога есть поля `Source` (`Manual` / `Mis`), `ExternalId`, `SyncedAt`. Сейчас каталог ведётся руками в админке. После выбора МИС фоновая синхронизация (`ICatalogSource`) по `ExternalId` обновляет название, цену и длительность. Описание для сайта, фото, видимость и порядок синхронизация **не трогает**: это редакторские поля.
- Каждое изменение цены пишется в `PriceHistory` (кто или что, когда, было → стало). Это нужно для разборов «почему на сайте была другая цена».
- Каталог используют и сайт, и запись, и визиты со сценариями напоминаний, и позже боты. Поэтому он живёт в своей схеме `catalog`, а не внутри страниц.
- **Уточнено в [ADR-0008](0008-care-scenarios.md) §2:** каталог — модуль `Catalog` **в `ClinicHub.Api`** (схема `catalog`, миграции сервера). Сайт читает его через API сервера, веб-админка правит его через этот же API.

### 3. Общие настройки и медиа
- `SiteSettings` — одна запись: название, телефон, адрес, часы, лицензия, ссылки на каналы и отзывы, пункты меню.
- `MediaFile` — метаданные картинок (имя, тип, размер, alt-текст). Сами файлы лежат на диске сервера в папке данных (`C:\ClinicHub\Data\media`), а не в БД. Папка входит в бэкап (ARCHITECTURE §4).

> **Изменено (2026-10-18, решение Свята).** Картинки хранятся **в БД** (`site.MediaFiles.Data`, varbinary/bytea), а не на диске.
> Причина: несколько демо-компьютеров работают с одной базой на ноутбуке, и картинка с диска одного компьютера на других не появилась бы.
> Сайт отдаёт картинку по `/media/{id}` с годовым кэшем браузера (у новой картинки всегда новый id) и держит данные в памяти
> (до 256 МБ), поэтому в базу ходит один раз на картинку. Лимит — 5 МБ на файл; тип определяется по содержимому (JPEG, PNG, WebP, GIF),
> SVG не принимается. Бэкап картинок — вместе с базой. Если для прода в клинике это окажется тяжело (большая база), можно вернуться
> к диску, сохранив таблицу как метаданные.
- **Палитра** (добавлено 2026-10-18): в `SiteSettings` основной цвет, фон и текст (`#RRGGBB`); остальные оттенки считаются из них,
  админка предупреждает о контрасте ниже 4,5:1. У блока — фон из вариантов этой палитры (`Block.Style`), а не произвольный цвет,
  чтобы текст оставался читаемым.

### 4. Хранение
- **Та же база**, что у сервера: сейчас SQL Server, перед продом PostgreSQL (ADR-0009). У сайта своя схема `site` (страницы, блоки, настройки, медиа). Схема `catalog` (услуги, врачи, цены) принадлежит серверу (ADR-0008 §2).
- У сайта свой `DbContext` и своя таблица истории миграций (`site.__EFMigrationsHistory`). Миграции сайта и миграции сервера не пересекаются, поэтому работа над сайтом не конфликтует с переходом сервера на PostgreSQL.
- Пока `ClinicHub.Web` ходит в эти схемы напрямую. Когда Api и Web объединятся в один хост (ADR-0003, «Последствия»), контексты переедут в модули без изменения схемы.

### 5. Редактор (веб-админка, ADR-0005)
- Раздел `/admin` в `ClinicHub.Web` на Blazor interactive server. Публичные страницы остаются статическим SSR без JavaScript.
- Возможности: список страниц; блоки страницы с перетаскиванием и кнопками «выше/ниже»; добавить, скрыть, удалить блок; форма полей блока; предпросмотр черновика; «Опубликовать»; история версий и откат; каталог (категории, услуги, цены, врачи); медиатека; настройки сайта.
- Вход: на первом этапе локальные учётные записи редакторов в схеме `site` (хеш пароля через `PasswordHasher` ASP.NET). Позже — общий модуль Identity (ARCHITECTURE §3, роли Admin / Marketing). Админка доступна только из сети клиники (ADR-0001).

## Последствия
- `site-content.json` уходит. Его содержимое при первом запуске переносится в БД (сид), чтобы сайт выглядел как сейчас.
- Компьютеру, где стоит сайт, нужна СУБД сервера. Для показа хватит SQL Server Express, установщик (`deploy/web`) научится подключаться к ней.
- Нужен доступ сессий Claude к nuget.org: без пакетов EF Core код не собрать и не проверить. Поэтому код сайта собирается в локальной сессии у Свята.
- Задача 1.1 (AlDanosAl) и эта работа должны договориться об одной строке подключения (`ConnectionStrings:ClinicHub`) и об одной базе.
- Добавление нового типа блока — задача программиста: класс настроек, компонент, форма редактора.
