# ADR-0008. Визиты и сценарии напоминаний: рассылки сами планируются от посещений и процедур

- Статус: **принято** (2026-10-17, решение Свята)
- Зависит от: ADR-0002 (мастер-данные), ADR-0004 (Dikidi), ADR-0005 (веб-админка), ADR-0009 (СУБД), ADR-0007 (каталог услуг)

## Контекст
Клинике нужно напоминать пациентам о том, что следует из их визита: контрольная явка, повтор процедуры, курс из нескольких сеансов, «давно не были».
Сейчас у ClinicHub нет данных о визитах вообще. Есть только авто-правило «день рождения» (`AutoRule`).
Если администратор будет вручную выставлять каждое напоминание, это забудут делать. Нужны **заранее описанные сценарии**, которые сами планируют сообщения от посещений и выполненных процедур, а администратор при необходимости их правит.

## Решение

### 1. Визиты — собственная копия в ClinicHub
`Visit { PatientId, StartAt (UTC), DoctorName, Status, Source, ExternalId, ConfirmedBy, ConfirmedAt }` и `VisitService { VisitId, ServiceId, ServiceName }`.
- `Status`: `Planned` (запись есть, визита ещё не было) → `Completed` / `NoShow` / `Cancelled`.
- `ServiceName` — снимок названия на момент визита: переименование услуги в каталоге не должно менять историю.
- **Откуда берутся визиты:**
  - **Сейчас — оба пути вместе.** Адаптер Dikidi (только чтение, ADR-0004) раз в N минут забирает записи и создаёт или обновляет `Visit` со статусом `Planned`, `Source = Dikidi`. Администратор при уходе пациента подтверждает: «визит состоялся» плюс процедуры (подставлены из Dikidi, можно поправить). Если Dikidi отвалится, администратор отмечает визит руками (`Source = Manual`), и всё продолжает работать.
  - **После МИС**: визиты и услуги приходят из МИС (дельта и вебхуки), подтверждение администратором не нужно. Мастер визитов — МИС (ADR-0002).
- Сопоставление названий услуг Dikidi или МИС с каталогом: таблица `ExternalServiceMap { Source, ExternalKey → ServiceId }`. Непонятное название администратор один раз сопоставляет руками, дальше оно подставляется само.
- `Patient.LastVisitAt` пересчитывается по последнему `Completed` визиту.

### 2. Каталог услуг живёт в сервере (уточнение ADR-0007)
Визиты, сценарии, запись и боты ссылаются на одни и те же услуги. Поэтому каталог (`catalog.service_category`, `catalog.service`, врачи, история цен — поля из ADR-0007 §2) — это **модуль `Catalog` в `ClinicHub.Api`** (схема `catalog`, миграции сервера).
Сайт читает каталог через API сервера, а веб-админка через этот же API его правит. В схеме `site` у сайта остаются только страницы, блоки, настройки и медиа.

> **Временное отступление (2026-10-17, решение Свята).** Пока модуля `Catalog` нет (Issue #13), услуги и врачи лежат в схеме `site`:
> `site.CatalogServices`, `site.CatalogDoctors`, `site.CatalogDoctorServices` (миграция сайта `TemporaryCatalog`). Причина: демо-компьютеры
> работают с одной общей базой, и цены должны правиться в ней, а не в `site-content.json` на каждом компьютере. Ключи услуг и врачей
> (`Key`, они же id в адресах записи и в блоках) переносятся в каталог сервера как есть. Когда API каталога готов: перенести данные
> в схему `catalog`, `DbSiteCatalog` в `ClinicHub.Web` заменить клиентом API, таблицы `site.Catalog*` удалить миграцией сайта.

### 3. Сценарии
```
CareScenario            — «Контроль после ботулинотерапии», «Курс PRP: 4 сеанса», «Давно не были 6 мес»
  Purpose               — Service | Marketing (определяет проверку согласий, см. §5)
  Trigger               — VisitCompleted (с услугами из списка; пусто = любая) | NoVisitFor (N дней) | Birthday | Manual
  └── CareScenarioStep  — порядок, смещение в днях от события, время отправки (МСК), шаблон (варианты по каналам),
                          условия отмены: «есть будущая запись», «был визит после события», «была услуга X после события»
```
Примеры:
- *Контроль после ботулинотерапии*: Service, через 14 дней «Пора на контрольный осмотр, записаться: {ссылка_запись}». Отменяется, если пациент уже записан.
- *Повтор ботулинотерапии*: Marketing, через 4 месяца. Отменяется, если процедура уже была повторена.
- *Курс PRP*: Service, шаги на 14, 28 и 42 день. Каждый новый сеанс курса перезапускает цепочку.
- *Давно не были*: Marketing, NoVisitFor 180 дней, только если нет будущей записи.

### 4. Запланированные напоминания — видимые и редактируемые
`PlannedReminder { PatientId, ScenarioId?, StepId?, TriggerVisitId?, Kind (Scenario|Manual), Purpose, DueAt (UTC), Text, Status, StatusReason, CreatedBy, RequestId }`
- Когда визит становится `Completed`, планировщик сразу создаёт напоминания по всем подходящим сценариям. Незавершённые напоминания **того же сценария** для этого пациента отменяются, и цепочка начинается заново.
- В карточке пациента и на экране «пациент уходит» администратор видит, что и когда уйдёт. Там можно поменять дату или текст, удалить напоминание или добавить ручное («через N дней напомнить: …»). Это и есть ручной режим «на первых порах»: он работает поверх того же механизма.
- Перед отправкой фоновый воркер **ещё раз проверяет** условия отмены, согласия, отписку и то, не удалён ли пациент. Причину пропуска он записывает в `StatusReason`, чтобы было видно, почему сообщение не ушло.
- Отправка идёт через существующий конвейер (`SmsRequest` → очередь SIM; позже `ChannelRouter`) с лимитами SIM. **Окно отправки одно на всё** — часы из активной `RateConfig` (по умолчанию 9:00–20:00 по Москве); своего окна тишины у сценариев нет (уточнение Свята в PR #31, 19.10). Вне окна напоминания ждут его открытия. Время шага и ручного напоминания должно попадать в окно, иначе API отвечает 400 с понятной причиной. Пациенту уходит не больше одного напоминания в день: остальные сдвигаются на следующий день.
- Существующий `AutoRule` (день рождения) продолжает работать. Позже он переносится в сценарий с триггером `Birthday`.

### 5. Согласия и закон
- **Service** (контрольная явка, следующий сеанс назначенного курса) — это продолжение лечения по уже состоявшемуся визиту, отдельное рекламное согласие не требуется.
- **Marketing** («пора повторить процедуру», «давно не были», поздравление с предложением) — только при согласии на рекламу в этом канале (ст. 18 закона «О рекламе»). **Пока нет модуля Consents (PLAN 1.2), Marketing-напоминания создаются, но не отправляются** (статус `Skipped`, причина «нет модуля согласий»). Обходить это нельзя (CLAUDE.md).
- **Врачебная тайна** (ст. 13 закона 323-ФЗ): по умолчанию шаблоны не называют диагноз и процедуру («пора на контрольный осмотр», а не «после ботокса»). Решение, можно ли называть процедуру, — за клиникой и юристом.
- Деление сценариев на Service и Marketing утверждает клиника вместе с юристом. В админке рядом с полем `Purpose` стоит подсказка.

### 6. Где код
- `ClinicHub.Api/Modules/Catalog` — каталог услуг (общий).
- `ClinicHub.Api/Modules/Visits` — визиты, подтверждение, `ExternalServiceMap`.
- `ClinicHub.Api/Modules/Messaging/Scenarios` — сценарии, планировщик, `PlannedReminder`, воркер.
- `ClinicHub.Api/Modules/Integrations/Dikidi` — адаптер только на чтение.
- Экраны: в веб-админке (ADR-0005). Пока её каркаса нет, работа идёт через API (`.http`-файл и OpenAPI). Экраны добавляются отдельной задачей.

## Последствия
- Всё делается после задачи 1.1 (секреты, UTC), миграции — новые, поверх существующих (ADR-0009).
- Сайт берёт каталог из API сервера, а не из своей схемы (поправка к ADR-0007).
- Адаптер Dikidi хрупкий (ADR-0004). Если он сломается, деградация плавная: визиты отмечаются вручную.
- После внедрения МИС меняется только источник визитов, сценарии и напоминания остаются как есть.
